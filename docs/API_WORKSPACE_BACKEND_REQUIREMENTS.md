# 두리 워크스페이스에서 반드시 필요한 Backend 지원

기준일: 2026-08-23

## 공유 데이터와 권한

- 여행방, 참여자, 후보, 일정, 여행 사실, 잠금, 예약, 문서 연결과 TODO를 모든 참여자가 공유하는 단일 원본으로 저장해야 합니다.
- 모든 조회와 변경에서 여행방 멤버 여부와 역할을 검사해야 합니다.
- 잠긴 일정은 두리 제안 적용 중 이동·리사이즈·삭제·장소 교체되지 않아야 합니다. 사용자의 명시적인 잠금 해제 또는 변경은 별도 권한 검사 후 처리해야 합니다.
- 숙소와 복귀 지점은 표시명뿐 아니라 좌표, 외부 장소 식별값과 여행 지역 시간대를 함께 저장해야 합니다.
- 이동수단, 복귀 마감 시각, 이동·준비 여유시간에는 수정자, 확인 시각과 최신 버전이 필요합니다.

## 일정 저장의 일관성

- 일정 조회 응답에는 현재 일정 버전이 포함되어야 합니다.
- 일정 추가·수정·삭제·순서 변경과 티켓 변경은 사용자가 조회한 일정 버전을 기준으로 저장해야 합니다.
- 저장 직전에 버전을 비교하고, 충돌하면 최신 버전을 포함한 일관된 충돌 응답을 반환해야 합니다.
- 공유 일정 전체 저장과 자동 채우기 적용에서는 기준 버전 생략을 허용하면 안 됩니다. 여행방 멤버십과 현재 일정 버전을 데이터베이스 쓰기 조건에 함께 넣고, 일정 교체와 버전 증가를 하나의 조건부 쓰기 또는 transaction으로 커밋해야 합니다. 먼저 읽은 객체에서 버전을 비교한 뒤 별도로 저장하는 방식은 동시 요청을 막지 못합니다.
- 조건부 쓰기가 적용 대상을 찾지 못하면 파일 삭제 같은 부수 효과를 일으키지 말고 충돌로 종료해야 합니다. 제거된 티켓 파일 정리는 일정 커밋 뒤 실행하거나 재시도 가능한 작업으로 분리해야 합니다.
- 같은 요청이 재전송되어도 일정, 티켓 또는 연결 관계가 중복 생성되지 않아야 합니다.
- 일정 ID 중복, 여행 기간 밖 날짜, 잘못된 시간 범위, 일정 겹침, 존재하지 않는 장소와 권한 위반을 최종적으로 거부해야 합니다.
- `09:10–10:05`와 같은 임의의 분 단위를 손실 없이 왕복해야 하며 하루 끝 시각을 임의로 줄이거나 반올림하면 안 됩니다.

## 날짜와 DAY 변경

- 여행 날짜를 기준 데이터로 저장하고 DAY는 날짜에서 파생해야 합니다.
- Frontend가 계산한 영향 미리보기를 신뢰하지 말고 최신 공유 원본에서 잠금·예약·티켓 영향을 최종 재검증해야 합니다.
- 날짜 변경과 일정 이동·삭제는 같은 버전 검사와 transaction 안에서 모두 성공하거나 모두 취소되어야 합니다.
- 이 원자적 계약이 없을 때 Frontend가 날짜 변경과 일정 저장을 연속 요청으로 흉내 내면 안 됩니다.

## 예약·티켓·공유 문서

- 여행방 멤버만 접근할 수 있는 파일 저장소와 만료되는 안전한 다운로드 주소가 필요합니다.
- 파일 형식과 실제 내용, 크기, 접근 권한을 서버에서 검증해야 합니다.
- 일정 삭제나 장소 교체 시 Frontend의 영향 미리보기와 별개로 최신 잠금·티켓·문서 연결을 서버에서 다시 검사해야 합니다.
- 같은 일정 ID의 장소가 바뀌어도 이전 티켓이 새 장소에 자동 승계되면 안 됩니다.
- 파일 업로드·삭제와 일정 연결 변경은 모두 성공하거나 모두 취소되어야 하며 고아 파일이 남지 않아야 합니다.
- 사용자가 확인한 예약 사실과 원본 문서의 연결, 확인자와 확인 시각을 다른 기기에서도 동일하게 조회할 수 있어야 합니다.
- 티켓 이미지와 자유 메모만으로는 자동 채우기의 시간 제약 근거가 될 수 없습니다. 확인된 예약의 날짜, 시작·종료 시각 또는 허용 시간창, 지역 시간대, 장소·일정 연결과 원본 revision을 구조화해 제공하고, 빠진 값은 미확인 상태로 보존해야 합니다.

OCR 실행과 추출 결과 편집은 Frontend에서 할 수 있습니다. Backend에는 사용자가 확인한 결과를 안전하게 공유·동기화하는 계약만 필요합니다.

## 공유 TODO

- TODO는 기기 로컬 데이터가 아니라 여행방의 공유 데이터로 저장하고, 모든 참여자가 권한에 따라 같은 목록과 변경 결과를 확인할 수 있어야 합니다.
- 제목, 설명, 상태, 우선순위, 마감 날짜·시각·지역 시간대, 알림 시각, 담당자, 체크리스트, 생성자·수정자와 생성·수정·완료 시각을 손실 없이 저장해야 합니다. 날짜만 있는 마감과 시각까지 있는 마감을 구분해야 합니다.
- 담당자는 현재 여행방 참여자만 지정할 수 있어야 하며, 조회·생성·수정·완료·보관·삭제 권한은 여행방 역할에 따라 검사해야 합니다.
- 일정, 문서, 예약 사실과 연결할 수 있어야 하며 다른 여행방의 대상을 연결하는 요청은 거부해야 합니다. 연결 대상이 삭제되거나 변경될 때 TODO를 조용히 삭제하지 말고 연결 해제·해결·유지 중 정해진 결과와 영향을 반환해야 합니다.
- 수동 TODO뿐 아니라 두리 분석, OCR 확인 요청, 티켓·예약이 연결된 일정 변경으로 생성된 TODO의 출처와 기준 데이터 revision을 보존해야 합니다. 민감한 문서 원문이나 OCR 전문을 TODO 본문에 복제하면 안 됩니다.
- 같은 분석 이슈나 일정 변경 요청이 재전송되어도 자동 TODO가 중복 생성되지 않도록 여행방·생성 원인·원본 revision 범위의 안정적인 중복 방지 식별값을 받아 원자적으로 생성 또는 갱신해야 합니다.
- 자동 동기화가 사용자가 편집한 제목·설명·마감·상태·체크리스트를 덮어쓰면 안 됩니다. 원인이 해소되면 미편집 자동 TODO만 해결 상태로 전환하고, 사용자가 편집한 TODO는 보존해야 합니다. 사용자가 자동 TODO를 삭제하거나 보관한 기록도 같은 원인이 즉시 다시 생성되지 않도록 공유해야 합니다.
- TODO 조회와 변경에는 항목 revision을 포함하고 조건부 갱신을 지원해야 합니다. 충돌 시 다른 참여자의 변경을 덮지 말고 최신 항목을 포함한 충돌 응답을 반환해야 하며, 체크리스트 변경도 같은 규칙을 적용해야 합니다.
- 일정·문서 변경의 필수 후속 TODO는 원본 변경과 함께 transaction으로 저장하거나, 커밋된 변경에서 재시도 가능한 작업으로 반드시 생성되도록 해야 합니다. 일정만 변경되고 필요한 TODO가 누락되는 부분 성공을 허용하면 안 됩니다.
- 목록 조회는 진행 상태, 담당자, 마감일, 보관 여부 필터와 안정적인 페이지 구분을 지원해야 합니다. 마감·담당·상태 변경 알림은 중복 발송을 막고 사용자별 알림 설정과 여행 지역 시간대를 따라야 합니다.

TODO 내용 작성, 편집 UI, 두리 분석과 OCR에서 TODO 후보를 계산하는 로직은 Frontend가 담당할 수 있습니다. Backend에는 공유 원본, 권한, 일관성, 동기화와 알림 계약이 필요합니다.

## 참여자 성향 데이터

- 각 참여자가 제출한 성향 결과와 갱신 시점을 저장하고 여행방 분석에 사용할 최신 결과를 구분해야 합니다.
- Frontend 계산에 필요한 값에는 단위, 범위, 측정 해상도, 출처와 계산 방식이 함께 제공되어야 합니다.
- 응답이 없는 값을 중립값이나 0점으로 만들어 반환하면 안 됩니다.
- 원본 답변은 다른 참여자에게 노출하지 않고 조율에 필요한 파생 값만 권한에 맞게 제공해야 합니다.
- 후보별 필수 방문, 기피와 선호 강도처럼 일정 계산에 사용할 직접 입력을 참여자 및 후보와 연결해 저장해야 합니다.
- 계단·급경사·장거리 보행 같은 이동 제약은 여행방 참여 시점의 여행 유형 태그와 별개로 최신성·version이 있는 공유 근거로 보존해야 합니다. 다른 참여자에게는 원본 설문 대신 일정 계산에 필요한 최소 파생 제약만 제공하고, 값이 없거나 오래됐을 때는 제약 없음으로 간주하면 안 됩니다.

## 일관된 분석 기준과 제안 적용

- 여행방 사실, 참여자 성향, 후보, 장소 좌표, 일정, 잠금과 확정 예약의 버전을 같은 분석 기준으로 식별할 수 있어야 합니다.
- Frontend 분석 결과를 서버에 공유 저장하거나 일정·공유 TODO에 적용할 때 관련 공통 데이터가 바뀌었다면 최신 버전을 재검사해 거부해야 합니다. 기기 안의 분석 세션 stale 판정은 Frontend가 담당합니다.
- Frontend가 만든 일정 제안도 최신 일정 버전과 권한을 다시 확인한 뒤 전체 변경을 원자적으로 적용해야 합니다.
- 잠금 또는 확정 예약과 충돌하거나 실행할 수 없는 변경은 일부만 저장하지 말고 구체적인 실패 원인을 반환해야 합니다.

분석·조율·탐색 알고리즘 자체는 Frontend에서 실행할 수 있습니다. Backend Duri 결과를 정밀 분석의 근거로 사용하거나 서버 최적화 작업을 새로 만드는 것은 필수 조건이 아닙니다.

## 외부 근거 제공

- 비밀키가 필요한 길찾기와 공공데이터 호출은 Backend가 대리해야 합니다.
- 이동시간 결과에는 이동수단, 출발 시각, 거리, 소요시간, 제공처, 조회 시각과 시간 기준이 포함되어야 합니다.
- 자동 채우기로 새 후보를 끼우기 전에는 같은 일정 snapshot에서 `앞 일정 또는 하루 시작점 → 후보`와 `후보 → 뒤 일정 또는 하루 종료점` 각각의 실제 경로 근거를 조회할 수 있어야 합니다. 각 결과는 양 끝 장소·좌표의 식별값, 방문일과 출발 시각, 이동수단, 소요시간, 조회 시각과 유효기간이 일치해야 하며, 일부 구간만 확인된 결과로 적용을 허용하면 안 됩니다.
- 여러 후보의 전역 동선 최적화를 지원하려면 방향성 간선 묶음을 한 snapshot으로 조회하는 batch/matrix 계약 또는 optimizer가 요청한 간선만 중복 없이 가져오는 제한형 batch 계약이 필요합니다. 현재 단건 경로 API를 후보 `n`개의 `n(n-1)`쌍에 무제한 호출하는 방식은 사용하지 않습니다.
- 대중교통 결과에는 제공되는 경우 도보시간, 환승 수, 막차와 마지막 환승 정보를 포함해야 합니다.
- 조회 성공, 실제 이동 불가, 자료 없음과 공급자 실패를 서로 다른 상태로 반환해야 합니다.
- 현재 교통과 미래 출발 시각 예측을 구분하고 자료의 유효기간을 알려야 합니다.
- 장소 운영정보는 원문, 출처, 조회 시각과 장소 식별값을 제공해야 합니다. 자동 채우기 적용 근거로 쓸 때는 제안된 방문일의 지역 시간대, 요일별 운영 구간, 날짜별 휴무·예외와 마지막 입장 정보를 구분할 수 있어야 하며, 원문 일부 호출 실패를 빈 운영 제약으로 반환하면 안 됩니다. 해석과 제약 판정은 Frontend가 담당합니다.

Frontend 최적화기는 위 근거와 공유된 체류시간·시간창·일일 시작·종료 좌표, 참여자별 후보 효용이 모두 있을 때 계산할 수 있습니다. 신뢰 가능한 입력 공급만 Backend 책임이며 최적화 계산 자체를 서버에 새로 구현할 필요는 없습니다.

## API 계약

- Swagger 문서, 실제 응답과 저장 형식이 일치해야 하며 데이터베이스 내부 표현이 응답에 노출되면 안 됩니다.
- 각 변경 API는 권한 오류, 입력 오류, 버전 충돌과 외부 공급자 실패를 구분된 상태로 반환해야 합니다.
- 여행방·일정·예약·파일·TODO의 식별값과 관계가 모든 API에서 동일해야 합니다.

Frontend의 일정·분석·문서·TODO 화면과 자동 생성 로직 회귀 검증은 별도로 수행합니다. TODO 공유 저장, 실제 동시 수정, transaction, 권한, 알림과 기기 간 동기화는 Backend가 연결된 환경에서 검증해야 합니다.
